## 1.3. Версия и маршруты практики

Основная версия итогового проекта — Apache Spark 3.5.3 с Delta Lake 3.3.0. Проект запускается через Docker Compose: код выполняется в Jupyter, данные хранятся в MinIO, события поступают из Kafka, а готовые витрины используются в ClickHouse и Metabase.

Для этого маршрута ориентируйтесь на требования README: минимум 10 ГБ свободной оперативной памяти; рекомендуется 12–16 ГБ. Для упражнений с DataFrame API подходит более лёгкая среда, но она не заменяет проверку полного проекта с внешними сервисами.

В модулях 2–7 вы освоите операции над данными. Модуль 8 объясняет, как Spark выполняет запросы и почему один вариант обработки может быть дороже другого. Модуль 9 объединяет базовые навыки в практику. Модули 10–11 переводят работу в локальный стек с загрузкой, очисткой, историей изменений и аналитическими витринами.

Не обновляйте PySpark на произвольную новую версию посреди прохождения: вместе с версией могут измениться зависимости и поведение выражений. Например, в Spark 4.0 ANSI mode включён по умолчанию. Сначала воспроизведите пример в среде курса, затем сравните результат с другой версией.

## 2.1. Почему Spark может быть быстрее

Spark позволяет описывать цепочку преобразований как единый план и выполнять её параллельно. Он может уменьшать объём читаемых данных, объединять совместимые вычисления и повторно использовать сохранённые промежуточные результаты. Однако ускорение зависит от задачи, формата данных, плана выполнения и доступных ресурсов.

Spark не хранит автоматически весь набор данных в памяти. Чтение файлов, shuffle и spill на диск могут составлять существенную часть работы. Даже короткий запрос может оказаться дорогим, если требует перемещения большого объёма данных между исполнителями.

Поэтому мы будем спрашивать не «во сколько раз Spark быстрее», а «что именно выполняет этот план»: какие данные он читает, где фильтрует строки, где делает shuffle и какие результаты вычисляет повторно.

Историческая справка: известная статья Google о MapReduce опубликована в 2004 году. Для практики важнее различать модель выполнения конкретных систем, чем запоминать универсальные множители ускорения.

**Иллюстрация:** один запрос рядом с его физическим планом; цветом отметить чтение, фильтрацию, локальную агрегацию и обмен данными. Не рисовать всю цепочку как выполнение исключительно в RAM.

## 2.2. Ленивое выполнение

Преобразования DataFrame обычно строят план, который Spark выполнит, когда понадобится результат. Вызов `filter` описывает условие отбора, а `count` запрашивает число строк и запускает необходимое вычисление.

```python
filtered = df.filter(F.col("amount") > 100)
print("План фильтра построен")
n = filtered.count()
print(f"Вычисление завершено: {n}")
```

Между двумя сообщениями выполняется `count`. Нельзя говорить, что в этом промежутке Spark ничего не делает.

Ленивость не означает, что любой вызов до action полностью свободен от работы. Например, чтение CSV с определением схемы может потребовать дополнительного прохода по данным. Кроме того, `explain` помогает изучить план, а не получить все строки результата. Разделяйте построение плана, анализ схемы и выполнение обработки данных.

**Упражнение:** добавьте второй `count`, сравните задания в Spark UI, затем повторите эксперимент с осмысленно размещённым cache. Объясните, что изменилось; не считайте cache обязательным улучшением для любой цепочки.

## 2.3. Типы и денежные значения

Тип Python-объекта и тип столбца Spark — разные уровни. Python `int` не имеет фиксированной разрядности int32 или int64, а Spark `IntegerType` и `LongType` имеют ограниченные диапазоны. При переходе между ними проверяйте допустимые значения и схему.

Для денежных сумм удобно использовать целое число минимальных денежных единиц либо `DecimalType` с согласованными precision и scale. Decimal позволяет представлять десятичные значения в заданных пределах, но не отменяет правила округления и обработки переполнения. Валюту и смысл суммы также нужно определить явно.

Если сумма сначала считалась в `double`, финальное округление не устраняет все последствия предшествующих вычислений с плавающей точкой. Выберите представление денег уже на входе и сохраните его по всему пути до витрины.

## 3.4. when и otherwise

`F.when` строит условное выражение Column. Вызов `.otherwise(...)` задаёт результат для остальных строк и является методом этого выражения.

```python
df.withColumn(
    "amount_band",
    F.when(F.col("amount").isNull(), F.lit("unknown"))
     .when(F.col("amount") >= 1000, F.lit("large"))
     .otherwise(F.lit("regular"))
)
```

Здесь проверка NULL сделана явно. Если не задать `otherwise`, строки, не удовлетворившие ни одному условию, получат NULL. Порядок ветвей важен: Spark использует первую подходящую ветвь.

## 11.2/3. Границы транзакции SCD2

**Замена объяснения текущего примера, до переписывания кода:**

В этом демонстрационном варианте сначала закрывается прежняя версия клиента, затем отдельной записью добавляется новая. Каждая запись в Delta атомарна отдельно. Вместе они не образуют одну общую транзакцию: если выполнение остановится между ними, таблица может остаться без актуальной версии клиента.

Поэтому этот вариант ещё не готов для надёжной повторяемой загрузки. Следующий шаг — подготовить входные строки для одного MERGE, который закроет изменившиеся версии и вставит новые. Дополнительно нужно обработать новые ключи и доказать, что повтор той же выгрузки не добавляет версии. Атомарность одной записи сама по себе не обеспечивает идемпотентность всего алгоритма.

Для истории будем явно использовать интервалы `[valid_from, valid_to)`: начало включено, конец исключён. Время действия атрибутов приходит из контракта источника или снимка; время запуска notebook не следует автоматически считать временем изменения клиента.

**Иллюстрация:** две шкалы коммитов. На первой между закрытием и вставкой показан сбой и отсутствие актуальной версии. На второй один коммит публикует согласованный результат. Подпись отдельно поясняет, что replay проверяется своим тестом.

## Проверочная лабораторная для SCD2

Используйте маленький набор, который можно проверить вручную. Все события имеют фиксированное время; порядок и политика входящих изменений заранее определены.

| Сценарий | Вход | Ожидаемое свойство |
|---|---|---|
| Первая загрузка | Новый клиент A, город Москва | Одна версия, она актуальна |
| Изменение | A переехал в Казань | Старая версия закрыта в effective time, новая актуальна |
| Повтор | Тот же batch изменения | Содержимое истории не меняется |
| Без изменения | Новое наблюдение с прежними атрибутами | Лишняя версия не появляется |
| Новый ключ | Клиент B впервые встречается в updates | Создаётся первая версия B |
| NULL | У A NULL заменяется строкой и обратно | Каждое действительное изменение распознано |
| Два события | Два изменения A за один день | Результат соответствует объявленной гранулярности и правилу обработки |
| Ошибка выполнения | Прерывание вокруг записи | Опубликованное состояние сохраняет инварианты |
| Историческая аналитика | Факт до переезда и факт после | Каждый факт соединяется ровно с одной правильной версией |

Проверяйте состояние таблицы, а не только число строк. Для указанного сценария без удалений у каждого клиента должна оставаться ровно одна актуальная версия; интервалы не пересекаются; replay сохраняет тот же результат. Выполнить эти проверки нужно в целевых Spark и Delta, а не только в эмуляторе.

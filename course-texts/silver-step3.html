Код: Bronze → Silver

Работаем в 02_silver.ipynb на настоящем Spark 3.5.3, Delta 3.3.0, UTC. Выполните предыдущие ячейки этого notebook: они задают BATCH_ID, правила формата, функции проверки и очищают клиентов и счета. Фрагмент ниже — ячейка операций из того же notebook, не отдельная программа.

Сначала проверяем исходное значение, затем меняем тип

В этой лабораторной формат источника задан заранее. Денежные поля amount и balance приходят как текст: принимаем обычную десятичную запись с точкой и не более чем двумя знаками после неё, например 12, 12.3, 12.30. Обычные пробелы по краям допускаются. Запятая, экспонента и знак + в формат этого источника не входят.

Одного cast недостаточно: он может изменить значение. Поэтому готовый код сначала проверяет формат, затем возможность представить сумму как Decimal(18,2) и бизнес-правило: сумма операции положительна, баланс неотрицателен. Все суммы набора — в RUB; запрет отрицательного баланса относится именно к нашей лабораторной.

Исходная записьРешение SilverПочему
Сумма 12.30ПринятьФормат и бизнес-правило соблюдены
Баланс 0.00ПринятьНулевой баланс разрешён; для суммы операции ноль запрещён

Для CSV-полей client_id и account_id принимаем положительные целые ID: цифры 0–9, обычные пробелы по краям допустимы, значение должно помещаться в LongType. Отдельно проверяем связи: счёт должен ссылаться на принятого клиента, а операция — на принятый счёт.

У отклонённой строки сохраняем причину и исходный текст в диагностических колонках amount_raw, balance_raw, client_id_raw или account_id_raw — в зависимости от таблицы. Так можно объяснить отказ. В принятом Silver эти колонки не нужны. Правила формата уже даны в notebook: для прохождения урока самостоятельно писать регулярные выражения не требуется.

Операции: от исходного Kafka-сообщения до принятой записи

Bronze хранит исходный value вместе с Kafka metadata в s3a://bronze/transactions_raw_v2. Парсим JSON, выбираем batch, типизируем и проверяем ссылку на принятый счёт.

schema = "tx_id STRING, batch_id STRING, account_id BIGINT, amount STRING, currency STRING, tx_type STRING, merchant STRING, status STRING, ts STRING"
raw = spark.read.parquet("s3a://bronze/transactions_raw_v2")
parsed = raw.withColumn("d", F.from_json(F.col("value").cast("string"), schema))
malformed = parsed.filter("d IS NULL OR d.batch_id IS NULL")
malformed.write.format("delta").mode("overwrite").save("s3a://silver/v2/quarantine/malformed_json")
print("Сообщений без распознаваемого batch:", malformed.count())
tx = parsed.select("d.*").filter(F.col("batch_id") == BATCH_ID)
tx = (tx.withColumn("amount_raw", F.col("amount"))
      .withColumn("amount", F.when(F.trim("amount_raw").rlike(MONEY_PATTERN),
                                   F.col("amount_raw").cast("decimal(18,2)")))
      .withColumn("ts", F.to_timestamp("ts"))
      .join(accounts_clean.select("account_id").withColumn("account_exists", F.lit(True)), "account_id", "left"))
tx_clean = save_clean("transactions", tx, {
    "tx_id": F.col("tx_id").rlike(r"\S"),
    "account_id": F.col("account_id") > 0,
    "orphan_account": F.col("account_exists") == True,
    "amount_format": F.trim("amount_raw").rlike(MONEY_PATTERN),
    "amount": F.col("amount") > 0,
    "currency": F.col("currency") == "RUB",
    "ts": F.col("ts").isNotNull(),
    "status": F.col("status").isin("completed", "pending", "failed"),
    "tx_type": F.col("tx_type").isin("purchase", "withdrawal", "transfer", "refund"),
}, "tx_id")
tx_clean.printSchema()

Что делает готовая save_clean

Разделяет строки на принятые и отклонённые; у отклонённых сохраняет reject_reason и исходные значения. Затем убирает точные повторы и проверяет уникальность ключа. Разные записи с одним ID — конфликт, а не повод произвольно оставить одну через dropDuplicates(["tx_id"]).

Результат: s3a://silver/v2/transactions; отклонённые операции: s3a://silver/v2/quarantine/transactions. Эти таблицы пересчитываются для выбранного batch. Ошибки JSON и записи без batch сохраняются отдельно; историю SCD2 этот notebook не перезаписывает.
